# Agent 协作协议

## 定位与角色

WebWeave 面向弱代码用户，通过对话和实例预览逐步完成简单网页制作、复杂前端优化、局部样式美化，以及为已有后端生成前端，目标是交付可预览、可导出、可部署上线的项目。

| ID | 角色 | 职责与交付 |
| --- | --- | --- |
| `main` | 主 Agent | 用户沟通入口；维护共识、分阶段委派、汇总问题、核对交付 |
| `design` | 前端设计 Agent | 页面或组件设计；按需提供候选预览；说明样例与可复用部分 |
| `code` | 前端工程 Agent | 项目理解、生成与修改、接口对接、运行验证和部署准备 |
| `audit` | 质量检查 Agent | 只读检查，提供问题证据、影响、位置及验收结论 |
| `template` | 模板制作 Agent | 独立制作三文件模板，预览后由用户确认入库 |

保留现有 ID、自定义 Agent 及模型选择。旧角色只有名称、描述和指令均与旧默认值完全一致时才升级；编辑过的角色保留，公共协作规则仍由系统指令注入。

## 阶段与决策

按需求理解、方向确认、分步实现、检查交付推进，可跨多轮对话、返回上一步，或跳过不需要的阶段。简单修改无需固定经过设计和独立检查。

主 Agent 区分用户原话、已确认决定、推断和待确认事项，利用已有对话及上下文摘要维护共识。需求范围、视觉方向、重大改动和正式上线前，展示具体方案并取得用户确认；阶段内的常规实现自主完成。重大改动指改变已确认体验、业务流程、接口契约，或替换技术栈、广泛重构，不能只按文件数量判断。确认只适用于当时展示的范围，不能用沉默或 Agent 推断代替确认。

需要用户选择方向时，用通俗语言提供少量选项；多个样例属于可选功能，用户方向明确时跳过。优先提供代表性页面或局部样例，记录名称、路径和实例 ID，标明视觉示意、演示数据或真实接口。用户选定后交接该方案，避免完整开发全部候选。

## 委派契约

只有主 Agent 可调用 `call_agent`，顺序执行，每次委派拥有独立任务 ID 和上下文，共享当前运行文件。子 Agent 只推进当前阶段的明确任务。

`call_agent` 参数为 `agent_id`、`task`、`contract`、`timeout`。`task` 是本次目标，`contract` 包含：

| 字段 | 含义 |
| --- | --- |
| `phase` | 当前阶段 |
| `user_request` | 相关用户原始需求 |
| `context` | 必要背景、已有产物、待确认事项 |
| `confirmed` | 已确认决定及适用范围，字符串数组 |
| `assumptions` | 未经用户确认的推断，字符串数组 |
| `inputs` | 资料、文件、组件和预览引用，字符串数组 |
| `scope` | 操作范围、可修改文件和禁止事项，非空字符串数组 |
| `acceptance` | 可判断的完成条件，非空字符串数组 |
| `deliverables` | 预期交付物和路径要求，非空字符串数组 |
| `read_only` | 是否限制为只读任务；质量检查始终只读 |

子 Agent 收到 `task` 与 `contract` 的 JSON，按路径读取实际文件。兼容历史调用：无 `contract` 时仍接受原有任务文本；新工具定义要求提供契约。范围与验收要求由协作指令约束，不是任意终端命令的文件级沙箱。

## 交付与执行状态

被委派 Agent 的最后回复使用 `agent_result` JSON Schema：

| 字段 | 含义 |
| --- | --- |
| `status` | `completed`、`partial`、`blocked`、`failed` |
| `summary` | 实际结果摘要 |
| `artifacts` | 真实交付文件路径数组 |
| `verification` | 实际命令、结果及适用文件的字符串数组；未验证须明确说明 |
| `pending` | 未完成事项数组 |
| `questions` | 待主 Agent 处理的决定或问题数组 |
| `previews` | 预览数组，每项含 `name`、`instance_id`、`purpose`、`data_source` |

无内容的数组为 `[]`。`completed` 不能带待办或问题；`partial` 必须说明待办；`blocked` 必须说明所需信息、决定或前置条件。遇到已确认决定冲突时返回 `blocked`，主 Agent 先检查已有资料，再决定是否询问用户。

工具返回保留 `ok`、`agent_id`、`agent_name`、`output`，增加 `subagent_id`、`execution_status`、`execution_reason` 和 `result`。`ok` 只表示执行是否正常结束，业务结果看 `result.status`。执行状态为 `completed`、`failed` 或 `stopped`；原因区分 `normal`、`error`、`timeout`、`cancelled`、`budget_reached`、`invalid_result`。

格式无效时在模型事件中保留原文：主对话暂停为 `blocked`，子任务向主 Agent 返回受阻交付，不把普通文本或无效 JSON 判为完成。声明 `completed` 时还核对持久工作记录：不得遗留待办、问题或失效验收；有契约时，`checks.name` 须逐项对应 `contract.acceptance`，状态为当前文件与需求版本的 `reviewed` 或 `passed`。缺少这些记录时转为 `partial` 并继续。有效 `partial` 结果由同一任务继续推进，文件变化、新观察和新验收状态均可构成进展；连续两次没有进展时暂停。工具轮次预算只控制执行分段，不撤掉工具请求收尾；`budget_reached` 保留兼容旧结果，新任务通过 `task_yielded` 交接并自动续段。调用标记文本（例如 DSML）不作为可执行工具或完成证明。

`subagent_started` 记录契约；`subagent_finished` 保留原执行状态并附加业务结果，兼容历史事件。界面优先展示业务状态，停止时保留停止状态；结构化交付转为可读文字，不展示流式 JSON 碎片。

## 检查点与调度

每项任务在 `tasks/{任务ID}.json` 保存独立的上下文、工具记录、父任务、当前分段及状态。主对话状态记录根任务 ID，委派工具记录关联稳定子任务 ID。模型产生的待执行调用先保存，每次工具开始前标为执行中，完成后将结果与配对上下文原子保存。恢复优先读取检查点，不使用会丢弃未配对调用的旧上下文修补逻辑。中断期间的新用户反馈排队保存：未开始的旧操作配对 `USER_FEEDBACK_SUPERSEDED` 取消结果，不先执行旧写入；正在等待的子任务保留身份并接收新反馈。已开始的写入先核对实际结果，未知副作用操作保持恢复决策；用户明确批准的重试仅释放对应调用，不放行其他过期操作。

达到分段预算返回调度器，保存进度后继续同一任务。`call_agent.timeout` 作用于委派中的每次模型请求，不再截断整个委派。父任务等待未完成子任务，恢复使用 `subagent_resumed`，不会创建新的重复会话；暂停用 `subagent_paused`。用户停止会取消当前请求并保留主子等待关系，服务重启后由“继续”恢复，不自动重放。

连续两个分段没有项目文件版本变化、新的文件/资料观察或有效检查证据时停止当前步骤。文件读取按规范路径、完整内容哈希及字符区间合并覆盖范围，改变 `max_chars`、超时或路径写法不能制造新进展；历史文件片段与原读取共用身份。连续六次未取得新内容的读取会提前收敛。子 Agent 将受阻业务结果和已有证据返回主 Agent，由主 Agent 安排具体下一步或如实交付可用部分；主 Agent 自身停滞才将运行置为 `blocked`。需要用户回复时进入 `awaiting_user`。文件产物进展与命令缓存仍使用路径、大小和修改时间版本，跳过已知探测文件仅用于产物进展判断，不代替验收。

`update_task_state` 维护本任务阶段（requirements/design/implementation/verification/review/delivery/deployment）、当前步骤、完成项、待办、问题证据、验收项及下一步；每类活动事实最多 12 条。旧待办和问题自动保留，稳定 ID 在 `open_items` 中提供；显式解决或撤销使用 `resolved: [{"id":"事项ID","evidence":"解决证据或撤销原因"}]`，解析无效时不改变已有工作记录。验收项按原 `name` 更新，遗漏时保留；需求变更使旧验收失效时，可通过同一 `resolved` 字段引用 `checks.id` 撤销，不能删除当前契约的必需验收。角色委派初始化阶段与契约，用户确认仍由真实决策记录决定。连续读取六次后必须先保存工作结论；重复更新记录本身不算进展，同一验收状态、文件版本和需求版本只计一次新证据。记录随检查点恢复并在每次模型请求注入，摘要不会替换它。

验收区分 `reviewed`、`passed`、`failed`、`unverified`；`passed` 引用当前文件版本真实成功的终端调用 ID，可用 `task_id` 指定同一运行中的其他任务。同任务可省略 `task_id`。`verification_evidence` 提供至多 12 条当前版本成功验证的任务 ID、调用 ID、命令及结果片段引用；只读角色通过 `read_context_segment` 核对结果，无需重新执行终端。项目版本或本任务用户反馈变化后，旧验收标为 `unverified`，证据和问题仍保留，当前采用项目整体失效策略。只读角色可更新自身工作记录和引用已有证据，不能因此获得项目写入或终端权限。

非阻塞限制、建议和用户明确接受的取舍写入 `work.notes`，在交付中如实披露，不放入阻塞性的 `pending`、`findings`。旧问题转备注时仍须显式 `resolved` 原 ID；仅新增备注不会清除旧问题，必需验收缺少证据时仍不能完成。`notes` 不表示缺陷已修复或验证已通过，也不授予权限。完成检查生成的待办提示仅反馈给模型，不复制为新的持久事项，原始问题及其 ID 保持不变。

在最终助手回复后点击“继续”会记录 `continuation=true` 的用户消息，建立新的用户轮次，避免部分思考模式接口把旧交付回复当作尚未结束的思考轮次而拒绝请求。消息明确保留原任务和已有授权，不改变需求版本、不授予新的确认；待执行工具仍优先按检查点恢复，不插入额外轮次打断调用配对。

模型预算、实际用量校准和原文范围读取见 README 的“上下文压缩与热加载”。摘要在应用层限制规模，超出部分保存完整原文并通过 `archive` 引用。成功批次在任务检查点保存摘要与剩余历史；后续失败或重启时，同一历史和配置从未完成批次恢复，不提交半成品摘要。常规压缩后仍超预算时，大块材料转为可分页回读的原文引用；必要指令仍无法容纳时明确停止。任务摘要只整理历史，不能授予权限或覆盖持久工作记录；不存在“摘要未展开源码所以必须从头审阅”的要求。

已经完成的工具直接复用其保存结果；执行中断的写文件操作先比较完整文件内容，新开实例先查询中断后新增的实例记录。终端等结果未知的操作生成恢复决策，不自行重放。用户明确允许重试只释放对应调用，不能通过普通“继续”绕过。

## 权限、检查与交付边界

质量检查及 `read_only` 任务只允许更新本任务工作记录、文件/上下文读取、Skill 读取、无下载的搜索和实例状态查看。工具定义隐藏项目写入与终端能力，执行入口再次拒绝越权调用，包括启动、停止、重启实例。任意终端命令难以保证只读，因此需要运行验证时，由主 Agent 委派工程角色执行并回传证据。

检查与修复基于实际证据。只有对应文件发生变化或出现新证据时才重查相关部分；不重复审计轻微问题，不把文件存在、源码检查、预览或单项委派完成等同于项目验收。

文件相关的只读终端验证声明 `intent=verify`，结果在 `verification.json` 保存并按命令参数和项目版本复用，超时参数不影响证据身份。验证和发布使用的版本包含临时检查脚本的变化，只有进展判断排除已知临时探测文件，避免检查器变化后误用旧证据。同一版本同一检查连续失败两次后暂停。`verify` 命令不得改文件或依赖时变外部状态；运行环境、HTTP 健康、进程等检查使用 `inspect`。命令用途由 Agent 声明，不解析任意脚本的真实业务语义。

首次实现要求用户确认具体需求与视觉方案。当前对话 Agent 用 `request_user_decision` 提出 `plan`、`change`、`deploy` 或 `question`；子 Agent 返回问题，由主 Agent 汇总。待决策内容持久化在运行状态中，WebUI/CLI 的真实用户操作记录批准，模型的 `confirmed`、用户沉默或普通文字修改均不授予权限。决策 ID 过期时拒绝操作，等待决策时拒绝直接“继续”。重大改动重新请求 `change` 会撤回原实现许可；发布确认绑定文件版本，文件变化后声明 `intent=deploy` 的命令需要重新确认。哪些业务变动属于重大改动、终端命令是否为发布，仍需 Agent 正确识别和声明。

本协议不新增导出入口、部署平台或账号集成。实际上线仍需目标平台、配置、必要凭据及用户针对具体发布方案的确认；已有的目录和终端运行边界不等同于操作系统级沙箱。

`plan` 携带候选方案时，WebUI 展示具体选择按钮，CLI 支持输入编号或完整选项。服务器要求选择具体方案，记录 `selection` 后授予该方案确认；不接受笼统 approve 来默认选择某一项。需要先看样例等偏好问题可先使用 `question`，再单独确认实现范围。
